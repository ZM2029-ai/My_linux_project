# EdgeLink：基于 i.MX6ULL 的轻量级物联网平台开发计划

## 1. 项目概述

### 1.1 项目名称

**EdgeLink——轻量级边缘物联网平台**

### 1.2 项目目标

基于 i.MX6ULL 开发板，开发一个具备设备接入、数据采集、消息通信、数据存储、远程控制和可视化管理能力的轻量级物联网平台。

项目采用渐进式开发方式，从基础 Linux 应用程序和网络通信开始，逐步搭建完整的平台。

### 1.3 项目定位

本项目不是简单的传感器数据采集程序，而是一个以 Linux 边缘网关为核心的轻量级物联网系统。

核心组成：

- **i.MX6ULL 开发板：** 负责设备接入、消息处理、数据存储和业务逻辑。

- **Windows 电脑：** 负责代码编写、交叉编译、测试和网页管理。

- **网页管理端，上位机：** 查看设备状态、历史数据、告警信息，并下发控制命令。

        │                         │

        │          │              │

        │          │              │

        │          │              │
        │   SQLite 数据存储        |
        └────────────┬────────────┘
                     │
             MQTT / TCP / 串口
                     │
        ┌────────────▼────────────┐

        │                         │
        │ 初期：电脑模拟设备         │

### 2.1 设计原则

1. 采用单体应用架构，暂时不拆分微服务。
2. 核心业务逻辑由自己编写，基础通信和存储能力优先使用成熟组件。
3. 使用模拟设备，写python模拟信号在windows电脑上，通过TCP传输给Linux设备。
4. 每个阶段都需要能够运行、测试和演示。
5. 所有开发均考虑 i.MX6ULL 的 CPU、内存和系统资源限制。

## 4. 开发环境规划

### 4.1 Windows 开发环境

主要负责：

- 使用 VS Code 编写和阅读代码。
- 使用 Git 管理项目。
- 使用 AI Agent 辅助开发、代码审查和调试。
- 访问网页管理端。
- 运行模拟设备程序或相关测试工具。

### 4.2 Ubuntu 虚拟机

主要负责：

- 配置 Linux 开发环境。
- 配置交叉编译工具链。
- 使用 CMake 构建项目。
- 检查编译结果的架构和动态库依赖。
- 管理适用于目标板的第三方库。

Ubuntu 虚拟机的版本和工具链需要根据目标板环境选择，不预先假定某个工具链一定兼容。

### 4.3 i.MX6ULL 开发板

主要负责：

- 运行网关程序。
- 接收并处理设备数据。
- 存储业务数据。
- 提供 HTTP API。
- 执行远程控制命令。
- 运行后续接入的真实硬件驱动或适配程序。

## 5. 分阶段开发计划

## 阶段一：开发环境准备与工程骨架搭建。

### 任务

1.确认 i.MX6ULL 开发板的 CPU 架构、操作系统版本、glibc 版本和 C++
运行库版本。

2.根据开发板现有系统选择兼容的交叉编译工具链和第三方库，避免生成依赖高于目标板运行环境的程序。

3.在项目目录中建立 Git 仓库和 CMake 工程，规划
`src`、`include`、`config`、`logs` 等目录。

4.编写最小 C++ 程序，完成交叉编译、部署到开发板和运行验证。

5.建立基础日志输出方式，记录程序启动、错误和关键运行信息。

6.整理 Windows 编写代码、Ubuntu 交叉编译、SSH/SCP 部署到 i.MX6ULL
的开发流程。

### 验收标准

- 能够说明目标板的主要系统环境和二进制兼容性要求。
- 能够在 Ubuntu 虚拟机中构建适用于目标板的最小 C++程序，并在开发板上运行。
- 能够将程序部署到开发板，查看运行结果和基本日志。
- 工程能够通过 Git 进行版本管理和恢复。
- 明确后续第三方库的交叉编译或部署方式。

## 阶段二：Linux 系统编程TCP通信实现音乐的流式播放

音乐播放模块独立运行，不要求就如MQTT，也不作为MQTT业务链路的一部分

### 任务

1. **Windows 端开发 TCP 音乐发送程序**：使用 Python 编写 TCP 客户端或服务器程序，读取本地 MP3 文件，并通过 TCP 连接持续发送音频数据。

2. **i.MX6ULL 开发板开发 TCP 音乐接收程序**：使用 C++ 编写 Linux TCP 通信程序，接收 Windows 端发送的音频数据，并将数据写入内存缓冲区，不保存完整 MP3 文件。

3. **实现音频流式处理**：在开发板上接入 MP3 解码模块，将接收到的 MP3 数据逐步解码为 PCM 音频数据。

4. **实现音频输出**：通过 Linux ALSA 音频接口调用 WM8960 声卡，将解码后的音频输出至开发板的 3.5 mm 耳机接口。

5. **实现连续播放机制**：设计内存缓冲区，协调网络数据接收、MP3 解码和音频播放，尽量避免因网络传输波动造成的播放中断。

6. **完成系统联调**：在 Windows 和 i.MX6ULL 开发板之间建立 TCP 连接，实现 MP3 音乐从 Windows 端发送、开发板实时接收并通过耳机播放的完整流程。

### 验收标准

1. Windows 端能够成功连接 i.MX6ULL 开发板，并建立稳定的 TCP 通信。

2. Windows 端能够发送本地 MP3 文件的数据流，开发板能够正确接收并处理数据。

3. 开发板不需要保存完整的 MP3 文件，即可通过内存缓冲、MP3 解码和 ALSA 音频输出实现流式播放。

4. 音乐能够通过开发板的 3.5 mm 耳机接口正常播放，声音连续、内容基本完整。

5. 能够正确处理 TCP 数据分段与多次接收的情况，不能假设一次 `recv()` 就能收到完整的音频数据块。

6. 具备基本的连接断开、数据发送结束和播放结束处理能力，音乐结束后能够正常释放缓冲区、关闭连接和音频资源。

7. 在正常局域网环境下，音乐能够在接收过程中开始播放，不必等待整首 MP3 传输完成；播放过程中无持续性卡顿。

## 阶段三：MQTT 消息通信

### 任务

1.理解 MQTT 中 Broker、Publisher 和 Subscriber
的作用及消息发布/订阅流程。

2.根据 i.MX6ULL 的系统环境，选择适合目标板的 Mosquitto 部署方式。

3.选择与目标板兼容的 C++ MQTT 客户端库。

4.在 Windows 上编写 Python 模拟设备程序，定时生成设备数据并发布 MQTT
消息。

5.在 i.MX6ULL 上编写 C++ 网关模块，订阅并接收模拟设备上报的数据。

6.设计设备遥测、在线状态、控制命令和命令响应等 MQTT 主题。

7.实现基本的连接状态管理和断线重连。

### 初步主题设计

```text
edgelink/device/{device_id}/telemetry
edgelink/device/{device_id}/status
edgelink/device/{device_id}/command
edgelink/device/{device_id}/response
```

### 验收标准

- MQTT Broker 能够按设计启动并接受客户端连接。
- Windows 上的模拟设备能够定时发布数据。
- i.MX6ULL 网关能够订阅主题并接收设备数据。
- 能够区分不同设备的消息，并识别设备在线和离线状态。
- 网络或 Broker 短暂中断后，程序能够按设计尝试恢复连接。
- MQTT 通信模块能够独立测试，并可供后续设备管理模块调用。

## 阶段四：设备管理与数据存储

### 任务

使用 SQLite 存储数据，并通过 C++ 业务层统一访问数据库。

1.设计设备信息、遥测数据和操作记录的数据结构。

2.使用 SQLite 存储设备信息、设备状态、历史遥测数据和必要的操作记录。

3.在 C++ 业务层封装数据库访问逻辑，避免数据库操作散落在各个模块中。

4.实现设备注册、设备信息查询和设备状态更新。

5.将 MQTT 接收到的遥测数据解析后写入数据库。

6.实现按设备标识和时间范围查询历史数据。

### 验收标准

- 能够添加、查询和更新设备信息。
- 网关能够把模拟设备上报的数据写入 SQLite。
- 程序重启后，已保存的设备信息和历史数据仍然存在。
- 能够按设备标识和时间范围查询历史数据。
- 数据库操作失败时能够记录错误日志，不导致程序无提示地异常退出。

## 阶段五：HTTP API 与网页管理端

### 任务

1.为 i.MX6ULL 网关设计并实现 HTTP REST API。

2.提供设备列表、设备详情、设备状态和历史遥测数据查询接口。

3.使用 HTML、CSS 和 JavaScript 开发运行在 Windows 浏览器中的管理页面。

4.在页面中展示设备列表、在线状态和最新遥测数据。

5.为历史数据提供基本的查询和曲线展示功能。

6.为请求加载、空数据、接口失败等情况提供明确的页面反馈。

7.由 HTTP API 统一调用设备管理和数据库模块，避免网页直接访问数据库。

### 验收标准

- Windows 浏览器能够访问管理页面。
- 页面能够显示开发板保存的设备数据。
- 用户可以查询设备和历史记录。
- API 出错时能够显示明确的错误信息。

## 阶段六：远程控制、告警与公网访问

### 任务

1. **实现本地远程控制：** 在网页管理端增加模拟设备的数据上报启停控制入口。网关验证控制命令后，通过 MQTT 下发至对应模拟设备，并接收执行结果。

2. **完善控制流程：** 为控制命令设计必要的参数校验、命令标识、执行结果和超时处理机制，并记录控制操作及执行结果。

3. **实现用户身份验证：** 为管理端增加登录或访问认证机制，对设备数据查询和远程控制设置必要的访问权限。网关必须在服务端验证控制请求，不能仅依靠前端界面限制操作。

4. **配置临时公网访问：** 在 Windows 或 Ubuntu 虚拟机上部署适用于开发测试的隧道客户端，使用临时公网地址转发至 i.MX6ULL 提供的 HTTP 服务。确认隧道运行环境能够访问开发板上的 API，并且不需要为本阶段购买域名或长期租用云服务器。

5. **实现公网数据查询：** 通过临时公网地址访问网页管理端，查询开发板保存的设备信息、在线状态和历史数据。

6. **实现公网远程控制：** 登录管理端后，从外部网络下发模拟设备控制命令，并在网页中展示网关返回的执行结果。

7. **完善访问安全：** 只开放必要的 Web 服务入口，不直接向公网暴露 MQTT、SSH 等非必要服务端口；对未授权请求、非法控制参数和执行失败情况进行处理并记录日志。

8. **完成公网联调：** 在与开发板不同的网络环境中测试网页访问、数据查询、远程控制、连接中断和恢复等情况。演示结束后关闭临时隧道，停止不再需要的公网访问。

### 验收标准

- 用户能够在局域网内通过网页发起模拟设备控制命令，并查看执行结果。

- 未登录或未获授权的用户不能执行受保护的设备控制操作。

- 开发板能够通过 MQTT 将合法控制命令发送至模拟设备，并正确处理执行成功、失败和超时等结果。

- 不购买域名、不长期租用云服务器的情况下，能够使用临时公网地址访问管理页面和 HTTP API。

- 从与开发板不同的网络环境访问时，能够查询开发板实际保存的设备数据，而非仅展示静态网页内容。

- 授权用户能够通过公网下发控制命令，并查看真实的命令执行结果。

- 未授权请求和非法控制参数会被服务端拒绝；关键操作和异常情况能够记录日志。

- 网络或隧道中断后，系统能够给出明确的访问失败提示；重新启动隧道后，能够按照新的临时地址恢复演示。

- 演示结束后能够关闭公网隧道，避免服务在不需要时继续对外开放。

### 部署说明

本阶段采用临时隧道完成开发演示，不要求系统长期在线，也不要求固定公网域名。临时公网地址、隧道进程和访问权限均按单次演示进行管理。若后续需要长期在线或固定域名，再单独规划正式部署方案。
