# 阶段一：交叉编译环境搭建与验证（复现文档）

> **适用项目**：EdgeLink——基于 i.MX6ULL 的轻量级物联网平台
> **文档用途**：从零复现「能在 i.MX6ULL 开发板上运行的 C++ 交叉编译环境」
> **最后验证时间**：2026-10-28（全流程实测通过）
> **预计复现耗时**：15～30 分钟（取决于下载速度）

## 0. 本文档解决什么问题

本项目在 Ubuntu 24.04 虚拟机上用系统自带的 `arm-linux-gnueabihf-gcc`（GCC 13）编译程序，部署到 i.MX6ULL 开发板后无法运行，报符号版本缺失。

根因是**交叉编译工具链的运行库版本高于目标板**：

- 交叉工具链自带 glibc **2.39**、libstdc++（GCC 13），编译出的程序要求 `GLIBC_2.34` 等新符号；
- 开发板是 Debian 10 buster，glibc 只有 **2.28**、libstdc++ 最高只到 `GLIBCXX_3.4.25`。

本文档记录**已验证可行的替代方案**：在 Ubuntu 24.04 上用 `debootstrap` 建一个 Debian 10（buster）chroot，在 chroot 内使用与开发板同代的 **GCC 8.3** 交叉工具链完成编译、部署、运行全流程。

复现完成后应当达到：**最小 C++ 程序交叉编译后能通过 scp 部署到开发板并正常输出运行时环境信息。**

## 3. 核心约束：二进制兼容性

### 3.1 目标板的运行环境上限

程序在开发板上运行时，动态链接器只会满足开发板**已有**的符号版本：

| 运行库       | 板上版本         | 可接受的最高符号版本       |
| --------- | ------------ | ---------------- |
| glibc     | 2.28         | `GLIBC_2.28`     |
| libstdc++ | 8.3.0-6      | `GLIBCXX_3.4.25` |
| libgcc    | 与 GCC 8.3 同代 | `GCC_8.x` 以内     |

**超过上限的符号会导致程序启动直接失败**，典型报错：

```text
./app: /lib/arm-linux-gnueabihf/libc.so.6: version `GLIBC_2.34' not found
./app: /usr/lib/arm-linux-gnueabihf/libstdc++.so.6: version `GLIBCXX_3.4.28' not found
```

### 3.2 GCC 版本与符号版本对照（选择工具链的依据）

| GCC 版本                | libstdc++ 最高符号            | 能否在板上运行       |
| --------------------- | ------------------------- | ------------- |
| 7.x                   | `GLIBCXX_3.4.24`          | ✅ 可以          |
| **8.3（板上同代）**         | **`GLIBCXX_3.4.25`**      | ✅ **正好匹配，首选** |
| 9.x                   | `GLIBCXX_3.4.26`～`3.4.28` | ❌ 不行          |
| 10.x                  | `GLIBCXX_3.4.28`          | ❌ 不行          |
| 11.x                  | `GLIBCXX_3.4.29`          | ❌ 不行          |
| 12.x                  | `GLIBCXX_3.4.30`          | ❌ 不行          |
| 13.x（Ubuntu 24.04 默认） | `GLIBCXX_3.4.31` 以上       | ❌ 不行          |

除 libstdc++ 符号外，还要看**工具链自带 glibc 的版本**：Ubuntu 24.04 的交叉工具链带 glibc 2.39，从 glibc 2.34 起 `pthread_*` 等符号并入 libc 并升版，所以哪怕只用了 `std::thread`，也会要求 `GLIBC_2.34`。

### 3.3 失败方案实测证据（不要重复踩坑）

在 Ubuntu 24.04 上用系统自带 GCC 13 编译最小程序：

```bash
arm-linux-gnueabihf-g++ -O2 -pthread -o hello_arm hello.cpp
strings hello_arm | grep -oE 'GLIBC(X)?_[0-9.]+' | sort -uV | tail -4
```

实测输出：

```text
GLIBC_2.4
GLIBC_2.34      ← 板上没有，必然失败
```

结论：**Ubuntu 24.04 的系统交叉工具链不能用于本项目。**

> 注意：`-static-libstdc++` 只能解决 libstdc++ 部分，**glibc 的 `GLIBC_2.34` 需求依然存在**，所以静态链接 libstdc++ 不是本问题的解法。

## 4. 方案选型

### 4.1 候选方案对比

| 方案                                       | 做法                                                                              | 结论                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| A. Ubuntu 24.04 自带 GCC 13                | `apt install gcc-arm-linux-gnueabihf`                                           | ❌ 符号版本过高（已实测失败）                                                |
| B. ARM 官方 GNU-A 8.3 工具链                  | 下载 `gcc-arm-8.3-2019.03-x86_64-arm-linux-gnueabihf.tar.xz` 解压即用                 | ⭕ 可行，但官网（`developer.arm.com`）国内下载实测仅约 40 KB/s，200 MB 需近 1.5 小时 |
| **C. Debian 10 chroot + GCC 8.3**        | `debootstrap` 拉 Debian 10 到 `/opt/buster`，chroot 内装 `gcc-8-arm-linux-gnueabihf` | ✅ **采用**，走国内镜像速度快，且 GCC 8.3 与板上 `gcc 8.3.0-6` 完全同代             |
| D. Docker 内 ubuntu:18.04 / debian:buster | 容器里装 GCC 7.5 / 8.3                                                              | ⭕ 可行，但依赖 Docker 与镜像源可达性                                        |
| E. 板上本地编译                                | 板上 `apt install g++ make` 用 8.3 编译                                              | ⭕ 兼容性 100%，但单核 792 MHz 编译慢，且不符合「交叉编译」的验收要求，仅作兜底                |

### 4.2 为何选方案 C

1. **版本精确对齐**：Debian 10 的 `gcc-8-arm-linux-gnueabihf` 是 GCC 8.3.0-6，与板上 `gcc 8.3.0-6`、`libstdc++6 8.3.0-6` 完全同代，符号版本正好卡在 `GLIBCXX_3.4.25`。
2. **下载快**：Debian 10 的 buster 归档源国内可达（`mirrors.aliyun.com/debian-archive`，开发板自身的 apt 源就是这一套），实测速度远高于 ARM 官网。
3. **不污染宿主系统**：工具链装在 `/opt/buster` 里，Ubuntu 24.04 的包管理、系统库一律不动，也不需要删除已有的 GCC 13。
4. **可复现**：全部操作都是命令，本文档即可重建；chroot 目录删掉重来也就十几分钟。

### 4.3 方案 C 的已知代价

- chroot 里没有 `/proc`、`/dev` 等挂载点时会有警告（不影响编译）；
- 源码要能被 chroot 看到，需要 `mount --bind` 或拷贝（见 7.1）；
- 编译产物属主是 root，拷出后要 `chown`（见 7.3）；
- Debian 10 已 EOL，必须关闭 apt 的 `Valid-Until` 检查（见 5.3）。

## 5. 环境搭建步骤（一次性）

以下命令**全部在 Ubuntu 24.04 虚拟机内执行**，不需要 sudo 密码之外的其他东西。

### 5.1 安装 debootstrap

```bash
sudo apt update
sudo apt install -y debootstrap
```

### 5.2 创建 Debian 10 最小系统

```bash
sudo debootstrap --variant=minbase --arch=amd64 --no-check-gpg buster /opt/buster \
  http://mirrors.aliyun.com/debian-archive/debian
```

- `--variant=minbase`：只拉最小系统，体积小；
- `--arch=amd64`：chroot 自身运行在 x86_64 上（它是「编译机」，不是目标架构）；
- `--no-check-gpg`：使用的是归档源，签名链已过期，跳过验证；
- 预计下载 100～200 MB，国内镜像通常几分钟内完成。

**预期结尾输出**类似：

```text
I: Base system installed successfully.
```

### 5.3 chroot 内让 apt 可用

Debian 10 已 EOL，必须处理两件事：DNS 与归档源的 `Valid-Until` 过期检查。

```bash
# DNS：让 chroot 内能解析域名
sudo cp /etc/resolv.conf /opt/buster/etc/resolv.conf

# 关闭 Valid-Until 检查（归档源 Release 文件已过期，否则 apt 拒绝工作）
echo 'Acquire::Check-Valid-Until "false";' | sudo tee /opt/buster/etc/apt/apt.conf.d/99archive
```

### 5.4 安装交叉工具链

```bash
sudo chroot /opt/buster /bin/bash -c \
  "apt-get update && apt-get install -y --no-install-recommends \
   gcc-8-arm-linux-gnueabihf g++-8-arm-linux-gnueabihf make cmake git"
```

安装内容说明：

| 包                           | 作用                     |
| --------------------------- | ---------------------- |
| `gcc-8-arm-linux-gnueabihf` | C 交叉编译器（GCC 8.3）       |
| `g++-8-arm-linux-gnueabihf` | C++ 交叉编译器（GCC 8.3）     |
| `make` / `cmake` / `git`    | 后续构建与版本管理（阶段一任务 3 起使用） |

命令前缀说明：该包的二进制文件名为 `arm-linux-gnueabihf-gcc-8` / `arm-linux-gnueabihf-g++-8`（带 `-8` 后缀），不带后缀的 `arm-linux-gnueabihf-gcc` 来自 Ubuntu 24.04 自带的 GCC 13，**不要混用**。

### 5.5 验证工具链

```bash
sudo chroot /opt/buster /usr/bin/arm-linux-gnueabihf-gcc-8 --version | head -1
sudo chroot /opt/buster /usr/bin/arm-linux-gnueabihf-g++-8 --version | head -1
```

**预期输出**：

```text
arm-linux-gnueabihf-gcc-8 (Debian 8.3.0-6) 8.3.0
arm-linux-gnueabihf-g++-8 (Debian 8.3.0-6) 8.3.0
```

只要版本是 **8.3.0**，环境即搭建成功。

> 提示：`arm-linux-gnueabihf-gcc -dumpversion` 只打印主版本号（例如 `13`、`8`），要看完整版本必须用 `--version`。

## 6. 冒烟测试：编译 → 检查 → 部署 → 运行

### 6.1 测试源码

保存为 `/tmp/hello.cpp`（chroot 内将位于 `/work/hello.cpp`）：

```cpp
#include <iostream>
#include <string>
#include <thread>
#include <sys/utsname.h>
#include <gnu/libc-version.h>

int main() {
    utsname u{};
    std::string arch = "unknown", kernel = "unknown";
    if (uname(&u) == 0) { arch = u.machine; kernel = u.release; }

    std::cout << "EdgeLink smoke test" << std::endl;
    std::cout << "  arch          : " << arch << std::endl;
    std::cout << "  kernel        : " << kernel << std::endl;
    std::cout << "  glibc         : " << gnu_get_libc_version() << std::endl;
    std::cout << "  hw_concurrency: " << std::thread::hardware_concurrency() << std::endl;
    return 0;
}
```

设计意图：一次运行同时验证 **CPU 架构**、**内核版本**、**glibc 版本**、**线程库**四项，比单纯打印 Hello 更有诊断价值。

### 6.2 在 chroot 内交叉编译

```bash
sudo mkdir -p /opt/buster/work
sudo cp /tmp/hello.cpp /opt/buster/work/

sudo chroot /opt/buster /bin/bash -c \
  "cd /work && /usr/bin/arm-linux-gnueabihf-g++-8 -O2 -pthread -o hello_arm8 hello.cpp"

# 取出产物到普通用户目录
sudo cp /opt/buster/work/hello_arm8 ~/
sudo chown $USER:$USER ~/hello_arm8
chmod +x ~/hello_arm8
```

### 6.3 静态检查（部署前）

```bash
file ~/hello_arm8
echo "--- 需要的符号版本 ---"
readelf -V ~/hello_arm8 | grep -E 'Name: (GLIBC|GLIBCXX|CXXABI)' | sort -u
echo "--- 依赖库 ---"
readelf -d ~/hello_arm8 | grep NEEDED
```

**实测通过结果**：

```text
ELF 32-bit LSB pie executable, ARM, EABI5 version 1 (SYSV), dynamically linked,
interpreter /lib/ld-linux-armhf.so.3, for GNU/Linux 3.2.0, not stripped

Name: GLIBC_2.4
Name: GLIBCXX_3.4
Name: GLIBCXX_3.4.9
Name: GLIBCXX_3.4.17
Name: CXXABI_1.3
Name: CXXABI_ARM_1.3.3

NEEDED: libstdc++.so.6
NEEDED: libm.so.6
NEEDED: libgcc_s.so.1
NEEDED: libpthread.so.0
NEEDED: libc.so.6
```

判定：

| 项目              | 判据                          | 实测                | 结论   |
| --------------- | --------------------------- | ----------------- | ---- |
| 架构              | `ARM, EABI5 ... hard-float` | 符合                | ✅    |
| 最低内核要求          | ≤ 板上内核 4.19                 | `GNU/Linux 3.2.0` | ✅    |
| 最高 glibc 符号     | ≤ `GLIBC_2.28`              | `GLIBC_2.4`       | ✅ 富余 |
| 最高 libstdc++ 符号 | ≤ `GLIBCXX_3.4.25`          | `GLIBCXX_3.4.17`  | ✅ 富余 |
| 依赖库             | 板上均已安装                      | 5 个库均在            | ✅    |
| 链接器             | `/lib/ld-linux-armhf.so.3`  | 一致                | ✅    |

> PIE 说明：产物为 PIE（position independent executable），这是 Debian/Ubuntu 交叉工具链的默认行为。板上内核 4.19 + glibc 2.28 支持 PIE，无需特殊处理。

### 6.4 部署到开发板并运行

```bash
scp ~/hello_arm8 debian@10.192.110.142:/home/debian/
ssh debian@10.192.110.142 'chmod +x ~/hello_arm8 && ./hello_arm8'
```

- `scp`：通过 SSH 通道把文件从虚拟机拷到开发板（验证部署通道）；
- `ssh user@host '命令'`：在开发板上远程执行该程序（验证运行时兼容性）。

### 6.5 板上实测输出（通过标准）

```text
EdgeLink smoke test
  arch          : armv7l
  kernel        : 4.19.35-imx6
  glibc         : 2.28
  hw_concurrency: 1
```

四项全部与预期一致，**阶段一「交叉编译 + 部署 + 运行」链路确认打通**。

> 注意：SSH 能登录**不代表**程序能运行。SSH 只验证网络与账号；能跑起来才验证了动态库符号、加载器、PIE、ABI 的兼容性。两者是两件事，都要验。

## 7. 日常开发用法

### 7.1 让 chroot 看到源码目录（bind mount）

chroot 是一个独立的根文件系统，看不到宿主机的 `/home/xxx`。构建前把源码目录挂进 `/opt/buster/work`：

```bash
# 每次开机/重新进入需要挂一次（重启后失效）
sudo mkdir -p /opt/buster/work
sudo mount --bind ~/edgelink /opt/buster/work

# 查看是否挂上
ls /opt/buster/work

# 不需要时卸载
sudo umount /opt/buster/work
```

> 源码放在 Windows 还是虚拟机、如何同步，属于工程骨架设计的内容，另行确定。这里只约定「构建时源码必须对 chroot 可见」这一事实。

### 7.2 构建

```bash
# 单文件
sudo chroot /opt/buster /bin/bash -c \
  "cd /work && /usr/bin/arm-linux-gnueabihf-g++-8 -O2 -pthread -o build/app src/main.cpp"

# CMake（阶段一任务 3 之后）
sudo chroot /opt/buster /bin/bash -c \
  "cd /work && cmake -S . -B build && cmake --build build -j4"
```

### 7.3 产物权限

chroot 内以 root 编译，产物属主为 root，拷出后需修正：

```bash
sudo cp /opt/buster/work/build/app ~/
sudo chown $USER:$USER ~/app
```

### 7.4 清理与重建

| 操作     | 命令                                   | 说明         |
| ------ | ------------------------------------ | ---------- |
| 只清构建产物 | `sudo rm -rf /opt/buster/work/build` | 最快，日常用     |
| 重装工具链  | 重跑 5.4 节                             | 包管理出问题时    |
| 完全重建   | `sudo rm -rf /opt/buster` 后重跑第 5 章   | 约 15～30 分钟 |

## 8. 常见问题（真实踩坑记录）

| 现象                                                                     | 原因                         | 处理                                                                  |
| ---------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------- |
| 板上运行报 `version 'GLIBC_2.34' not found`                                 | 用了 Ubuntu 24.04 自带的 GCC 13 | 改用本文档 chroot 内的 `arm-linux-gnueabihf-g++-8`                         |
| 板上报 `version 'GLIBCXX_3.4.28' not found`                               | 同上，libstdc++ 版本过高          | 同上                                                                  |
| `debootstrap: no such script: buster`                                  | debootstrap 版本不识别 buster   | 换用 Debian 官方 debootstrap，或手动下载 buster 脚本                            |
| chroot 内 `apt-get update` 报 `Release file ... is not valid`            | 没关 `Valid-Until`           | 执行 5.3 节的 `99archive` 配置后重试                                         |
| chroot 内 `apt-get update` 报 DNS 解析失败                                   | 没复制 `resolv.conf`          | 执行 5.3 节第 1 条                                                       |
| `chroot: failed to run command '/bin/bash': No such file or directory` | debootstrap 未完成            | `sudo rm -rf /opt/buster` 后重跑 5.2                                   |
| 编译时报 `fatal error: xxx: No such file`                                  | 头文件缺失，或用了错误的编译器            | 确认调用的是 `/usr/bin/arm-linux-gnueabihf-g++-8`                         |
| 编译正常但运行报 `Permission denied`                                           | 拷贝后丢了可执行位                  | `chmod +x`                                                          |
| `arm-linux-gnueabihf-gcc -dumpversion` 显示 `13`                         | 命中了 Ubuntu 24.04 自带的工具链    | 用绝对路径 `/usr/bin/arm-linux-gnueabihf-gcc-8`，或把 PATH 前置到 chroot 的 bin |
| 从 ARM 官网下载工具链只有 40 KB/s                                                | 海外链路 + 单连接限速               | 用本方案（国内镜像）；或 `aria2c -x 8` 多线程、或找国内镜像                               |
| chroot 里 gdb 报缺少 `libncurses5`                                         | 24.04 去掉了该库                | 不影响编译；调试可在板上进行或另装                                                   |

## 11. 附录

### 11.1 命令速查卡

```bash
# ---- 进入 chroot ----
sudo chroot /opt/buster /bin/bash

# ---- 编译单个源文件 ----
sudo chroot /opt/buster /bin/bash -c \
  "cd /work && /usr/bin/arm-linux-gnueabihf-g++-8 -O2 -pthread -o build/app src/main.cpp"

# ---- 挂载/卸载源码目录 ----
sudo mount --bind ~/edgelink /opt/buster/work
sudo umount /opt/buster/work

# ---- 检查产物兼容性 ----
file build/app
readelf -V build/app | grep -E 'Name: (GLIBC|GLIBCXX|CXXABI)'
readelf -d build/app | grep NEEDED

# ---- 部署并运行 ----
scp build/app debian@10.192.110.142:/home/debian/
ssh debian@10.192.110.142 './app'
```

### 11.3 已知限制

1. 本方案依赖阿里云对 Debian 10 buster 归档源的持续提供；若该源下线，需改用 `archive.debian.org` 或改用方案 B/D。搭建成功后 `/opt/buster` 可离线使用，不受影响。
2. chroot 与宿主机共享内核，**不能**用它运行 ARM 程序（只能编译）；ARM 程序必须在开发板上运行（或另配 qemu-user 模拟）。
3. 当前工具链为 GCC 8.3，C++17 可用但**应避开 `std::filesystem`**（其完整实现需要 GCC 9 / `GLIBCXX_3.4.26`）。工程代码基线建议 **C++14**。
4. 本文档只覆盖「环境搭建 + 最小程序验证」，不含 Git 仓库、CMake 工程骨架、日志模块（阶段一任务 3/5）。
